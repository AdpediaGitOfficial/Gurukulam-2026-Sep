# UAT deployment — pnpm, no Docker

A single Linux host running PostgreSQL, Redis, the API and the console directly
under systemd. Everything here was run against this repository except the
systemd units and the nginx config, which are written from the same facts but
have not been executed on a real host.

---

## 0. What the box needs

| Requirement | Why |
| --- | --- |
| **Node 22 or newer** | `engines.node` is `>=22`, and the API uses `crypto.randomUUID` at the top level |
| **pnpm 10.33.0** | `packageManager` pins it; a different major resolves the workspace differently |
| **PostgreSQL 16** | The schema is Prisma-migrated; no extensions are needed |
| **Redis** (optional) | Login lockout only. See §7 — a *misconfigured* Redis is worse than none |
| **A reverse proxy with TLS** | Not optional in practice. See §6 |

```bash
# Node via nvm, so the box is not tied to its distro's packaging
curl -fsSL https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
. ~/.nvm/nvm.sh && nvm install 22 && nvm use 22

corepack enable && corepack prepare pnpm@10.33.0 --activate

sudo apt update
sudo apt install -y postgresql-16 redis-server nginx
```

## 1. Database

```bash
sudo -u postgres psql <<'SQL'
CREATE USER gurukulam WITH PASSWORD 'a-real-password-here';
CREATE DATABASE gurukulam_uat OWNER gurukulam;
SQL
```

The application user owns the database, because `prisma migrate deploy` issues
DDL. Do not hand it superuser.

## 3. Environment

**The API has no dotenv of its own.** `loadEnv()` reads `process.env` and
nothing else — a `.env` file currently works only because the Prisma client
bundles dotenv and loads the repository root `.env` as a side effect of being
imported. That is a side effect, not a contract, so set real environment
variables for anything you intend to keep running.

Write `/etc/gurukulam/uat.env`, readable only by the service user:

```ini
NODE_ENV=production

# ── Database ──────────────────────────────────────────────────────────────
DATABASE_URL=postgresql://gurukulam:a-real-password-here@localhost:5432/gurukulam_uat?schema=public

# ── API ───────────────────────────────────────────────────────────────────
API_PORT=4000
API_BASE_PATH=/api/v1

# Generate BOTH, and never reuse one for the other:
#   openssl rand -base64 48
JWT_ACCESS_SECRET=<48 random bytes>
JWT_REFRESH_SECRET=<48 different random bytes>
JWT_ACCESS_TTL=15m
JWT_REFRESH_TTL=30d

REDIS_URL=redis://localhost:6379
CRON_SHARED_SECRET=<16+ random characters>

# Only matters for direct API consumers — the console is a BFF and the browser
# never calls the API. Mobile clients and third parties go here.
CORS_ALLOWED_ORIGINS=https://uat.example.com

# ── Console ───────────────────────────────────────────────────────────────
# Server-side only, deliberately not NEXT_PUBLIC_. Loopback: the API does not
# need to be reachable from outside the box.
API_INTERNAL_URL=http://127.0.0.1:4000/api/v1
```

```bash
sudo install -d -m 0750 /etc/gurukulam
sudo install -m 0640 uat.env /etc/gurukulam/uat.env
```

The API validates this at boot and refuses to start if it is wrong — a missing
secret is then a failed deploy rather than a 500 at the first login. Under
`NODE_ENV=production` it additionally refuses a placeholder `change-me` secret,
and refuses the two JWT secrets being equal (sharing them lets a refresh token
be presented as an access token).

## 4. Migrate and build

```bash
cd /srv/gurukulam
set -a && . /etc/gurukulam/uat.env && set +a

pnpm --filter @gurukulam/db migrate:deploy   # prisma migrate deploy — never `migrate dev`
pnpm build                                    # contracts → db → api → web, in that order
```

`pnpm build` runs four tasks through Turborepo and takes about a minute on a
warm cache. The order matters and is declared, not incidental: the API and the
console both compile against `@gurukulam/contracts`, and the Prisma client is
generated by `@gurukulam/db`'s build.

**Do not run `pnpm db:seed` on UAT.** The seed is demo fixtures — colleges,
students, batches. Use §5 instead.

## 5. Create the first operator

An empty database has no way in: every screen requires a signed-in principal,
and the only account-creating screen is behind that. `bootstrap` is the one
door, and it refuses to run on a database that already has operators.

```bash
cd /srv/gurukulam/apps/api
BOOTSTRAP_ADMIN_EMAIL=ops@example.com \
BOOTSTRAP_ADMIN_NAME="Ops Lead" \
BOOTSTRAP_ADMIN_PASSWORD='at-least-twelve-characters' \
pnpm bootstrap
```

It creates the two system roles and one Super Admin in a single transaction,
with `mustReset` set — the first sign-in lands on the change-password screen.

## 6. TLS is not optional — read this before you test

Session cookies are `httpOnly` and `secure` whenever `NODE_ENV=production`:

```ts
secure: process.env.NODE_ENV === "production"
```

Over plain `http://` on a LAN address, the browser **accepts the login response
and then silently discards the cookie**. The next request has no session, so
the console bounces straight back to `/login` with no error shown anywhere.
This is the single most likely way a UAT deployment appears broken.

Three ways out, in order of preference:

1. **Terminate TLS in front of the console.** Correct, and what production
   will do anyway.
2. **Reach it over an SSH tunnel.** Browsers treat `http://localhost` as a
   secure context, so `secure` cookies are kept:
   `ssh -L 3000:127.0.0.1:3000 user@uat-host`, then open `http://localhost:3000`.
   Good for one tester, useless for a group.
3. Do not run the console with `NODE_ENV` unset to dodge this. `next start`
   sets it to `production` itself, and fighting that trades a visible problem
   for an invisible one.

```nginx
server {
    listen 443 ssl http2;
    server_name uat.example.com;

    ssl_certificate     /etc/letsencrypt/live/uat.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/uat.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        # The API trusts the proxy for client addresses; this is what it reads.
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 80;
    server_name uat.example.com;
    return 301 https://$host$request_uri;
}
```

The API is deliberately **not** proxied. The console is a BFF: the browser
talks only to it, and it talks to the API over loopback. Exposing the API
publicly is only needed when a mobile or third-party client exists — and then
it needs its own vhost and `CORS_ALLOWED_ORIGINS` set to match.

## 7. Redis, and when to leave it out

Redis backs login lockout only. Without `REDIS_URL` the API falls back to an
in-process store and logs that it has done so — fine for a single-replica UAT,
wrong for more than one, because five failed attempts spread across replicas
never trip a lockout.

**A configured but unreachable Redis is worse than no Redis.** The lockout
check awaits Redis without a fallback, so if the URL is set and the server is
down, every login attempt returns a 500 rather than failing open. If you are
not confident Redis will stay up on this box, leave `REDIS_URL` unset.

*(Failing open instead would allow unlimited password guessing during an
outage. Which of the two is right is a product decision, not an obvious one —
it is on the open-questions list, not settled.)*

## 8. systemd units

`/etc/systemd/system/gurukulam-api.service`:

```ini
[Unit]
Description=Gurukulam API
After=network.target postgresql.service redis-server.service
Wants=postgresql.service

[Service]
Type=simple
User=gurukulam
WorkingDirectory=/srv/gurukulam/apps/api
EnvironmentFile=/etc/gurukulam/uat.env
ExecStart=/home/gurukulam/.nvm/versions/node/v22.22.2/bin/node dist/main.js
Restart=on-failure
RestartSec=5
StandardOutput=journal
StandardError=journal

NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/srv/gurukulam

[Install]
WantedBy=multi-user.target
```

`/etc/systemd/system/gurukulam-web.service`:

```ini
[Unit]
Description=Gurukulam console
After=network.target gurukulam-api.service
Wants=gurukulam-api.service

[Service]
Type=simple
User=gurukulam
WorkingDirectory=/srv/gurukulam/apps/web
EnvironmentFile=/etc/gurukulam/uat.env
ExecStart=/home/gurukulam/.nvm/versions/node/v22.22.2/bin/pnpm start
Restart=on-failure
RestartSec=5

NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/srv/gurukulam

[Install]
WantedBy=multi-user.target
```

Absolute paths to the Node binary, because systemd does not read a login shell
and will not find an nvm-managed `node` on `PATH`. Check yours with
`readlink -f "$(command -v node)"`.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now gurukulam-api gurukulam-web
sudo systemctl status gurukulam-api gurukulam-web
```

## 9. Smoke test before handing it over

```bash
# The API answers, and its docs are generated from the contracts it validates
curl -fsS http://127.0.0.1:4000/api/v1/health && echo
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:4000/api/v1/docs

# The console renders its login page
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/login

# The schema is where the migrations say it should be
cd /srv/gurukulam/packages/db && pnpm exec prisma migrate status
```

Then, in a browser over **https**:

1. Sign in as the bootstrap operator — you should land on the change-password
   screen, not the dashboard.
2. Set a new password; you should land on the dashboard.
3. Settings → Countries → add one. Then a city, a college, a course, a trainer.
4. Batches → create a retail batch. The trainer picker stays disabled until a
   course is chosen, then offers only trainers approved for it.
5. Students → add a retail student → allocate them to that batch. One
   transaction writes the batch mapping, session access, ledger, installments
   and credentials — check the fee ledger shows the advance applied.

That path exercises every invariant that has an enforcement point in the UI.
If step 1 returns you to the login screen with no error, re-read §6.

## 10. Redeploying

```bash
cd /srv/gurukulam
git pull
pnpm install --frozen-lockfile
set -a && . /etc/gurukulam/uat.env && set +a
pnpm --filter @gurukulam/db migrate:deploy
pnpm build
sudo systemctl restart gurukulam-api gurukulam-web
```

Migrate before building, and build before restarting: the running code should
never be newer than the schema underneath it.

There is no zero-downtime story here and UAT does not need one — the restart is
a couple of seconds. Production will want two API replicas behind the proxy and
a rolling restart, which is also the point at which Redis stops being optional.

## What this deliberately does not cover

Email, WhatsApp and S3 are not integrated, by design. Certificate PDFs are not
generated. Payments are recorded, never collected — there is no gateway.

**Granting a college portal login shows the temporary password once, on the
page, and nothing emails it.** The API returns it a single time and stores only
its hash, so nobody can retrieve it afterwards — losing it means issuing a new
one, which invalidates the old. Whoever runs UAT needs a way to pass it on.

The college, trainer and student portals themselves are deferred. The API
accepts a `COLLEGE_USER` login today and the scope works, but there is no portal
UI behind it, so UAT covers the admin console only.
