# UAT deployment — npm, no Docker

A single Linux host running PostgreSQL, Redis, the API and the console directly
under systemd. Everything here was run against this repository except the
systemd units and the nginx config, which are written from the same facts but
have not been executed on a real host.

---

## 0. What the box needs

| Requirement | Why |
| --- | --- |
| **Node 22 or newer** | `engines.node` is `>=22`, and the API uses `crypto.randomUUID` at the top level |
| **npm 10** | Ships with Node 22. The repo is an npm workspace — nothing else to install |
| **PostgreSQL 16** | The schema is Prisma-migrated; no extensions are needed |
| **Redis** (optional) | Login lockout only. See §7 — a *misconfigured* Redis is worse than none |
| **A reverse proxy with TLS** | Not optional in practice. See §6 |

```bash
# Node via nvm, so the box is not tied to its distro's packaging
curl -fsSL https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
. ~/.nvm/nvm.sh && nvm install 22 && nvm use 22   # npm 10 comes with it

sudo apt update
sudo apt install -y postgresql-16 redis-server nginx
```

## 2. Check out and install

```bash
sudo mkdir -p /srv/gurukulam && sudo chown "$USER" /srv/gurukulam
git clone <repo-url> /srv/gurukulam
cd /srv/gurukulam
git checkout claude/project-analysis-6t08cr

npm ci
```

`npm ci` rather than `npm install`: it installs exactly what `package-lock.json`
records and fails if the lockfile and the manifests disagree, instead of quietly
resolving something that was never tested. It also wipes `node_modules` first,
so a redeploy cannot inherit a stale dependency.

## 3. Environment

**The API has no dotenv of its own.** `loadEnv()` reads `process.env` and
nothing else — a `.env` file currently works only because the Prisma client
bundles dotenv and loads the repository root `.env` as a side effect of being
imported. That is a side effect, not a contract, so set real environment
variables for anything you intend to keep running.

Write `/etc/gurukulam/uat.env`, readable only by the service user:

```ini
NODE_ENV=production

# ── Database ──────────────────────────────────────────────────────────────
DATABASE_URL=postgresql://gurukulam:a-real-password-here@localhost:5432/gurukulam_uat?schema=public

# ── API ───────────────────────────────────────────────────────────────────
API_PORT=4000
API_BASE_PATH=/api/v1

# Loopback. The console is a BFF and reaches the API over 127.0.0.1, so nothing
# else needs to. See §6a before changing this.
API_HOST=127.0.0.1

# Name the proxy — do not set `true`, and do not use a hop count. See §6a.
TRUST_PROXY=127.0.0.1

# The Swagger page and OpenAPI document bypass the auth guard. Off in
# production unless a third-party integrator actually needs them.
API_DOCS_ENABLED=false

# Generate BOTH, and never reuse one for the other:
#   openssl rand -base64 48
JWT_ACCESS_SECRET=<48 random bytes>
JWT_REFRESH_SECRET=<48 different random bytes>
JWT_ACCESS_TTL=15m
JWT_REFRESH_TTL=30d

REDIS_URL=redis://localhost:6379
CRON_SHARED_SECRET=<16+ random characters>

# Only matters for direct API consumers — the console is a BFF and the browser
# never calls the API. Mobile clients and third parties go here.
CORS_ALLOWED_ORIGINS=https://uat.example.com

# ── Console ───────────────────────────────────────────────────────────────
# Server-side only, deliberately not NEXT_PUBLIC_. Loopback: the API does not
# need to be reachable from outside the box.
API_INTERNAL_URL=http://127.0.0.1:4000/api/v1
```

```bash
sudo install -d -m 0750 /etc/gurukulam
sudo install -m 0640 uat.env /etc/gurukulam/uat.env
```

The API validates this at boot and refuses to start if it is wrong — a missing
secret is then a failed deploy rather than a 500 at the first login. Under
`NODE_ENV=production` it additionally refuses a placeholder `change-me` secret,
and refuses the two JWT secrets being equal (sharing them lets a refresh token
be presented as an access token).

## 4. Migrate and build

```bash
cd /srv/gurukulam
set -a && . /etc/gurukulam/uat.env && set +a

npm run db:deploy    # prisma migrate deploy — never `migrate dev`, see ADR 0003
npm run build        # contracts → db → api → web, in that order
```

`npm run build` runs four tasks through Turborepo and takes about a minute. The order matters and is declared, not incidental: the API and the
console both compile against `@gurukulam/contracts`, and the Prisma client is
generated by `@gurukulam/db`'s build.

`prisma migrate deploy` is safe to re-run: it applies what is missing and
nothing else. Confirm with `npm exec --workspace @gurukulam/db -- prisma migrate
status`, which should end **"Database schema is up to date!"** — there are
**9 migrations** as of this release.

The two most recent add columns only, with defaults chosen so existing rows keep
behaving as they did:

| Migration | What it adds |
| --- | --- |
| `20260908120000_in_house_trainers` | `trainers.engagement` (defaults to `FREELANCE`, so no existing trainer becomes staff) and `batch_trainer_assignments.auto_confirmed` (defaults false) |
| `20260908130000_assignment_release_reason` | `batch_trainer_assignments.release_reason`, nullable |

Neither rewrites data or drops anything, so a redeploy over an existing UAT
database needs no downtime beyond the restart in §10.

**Do not run `npm run db:seed` on UAT.** The seed is demo fixtures — colleges,
students, batches. Use §5 instead.

## 5. Create the first operator

An empty database has no way in: every screen requires a signed-in principal,
and the only account-creating screen is behind that. `bootstrap` is the one
door, and it refuses to run on a database that already has operators.

```bash
cd /srv/gurukulam/apps/api
BOOTSTRAP_ADMIN_EMAIL=ops@example.com \
BOOTSTRAP_ADMIN_NAME="Ops Lead" \
BOOTSTRAP_ADMIN_PASSWORD='at-least-twelve-characters' \
npm run bootstrap
```

It creates the two system roles and one Super Admin in a single transaction,
with `mustReset` set — the first sign-in lands on the change-password screen.

## 6. TLS is not optional — read this before you test

Session cookies are `httpOnly` and `secure` whenever `NODE_ENV=production`:

```ts
secure: process.env.NODE_ENV === "production"
```

Over plain `http://` on a LAN address, the browser **accepts the login response
and then silently discards the cookie**. The next request has no session, so
the console bounces straight back to `/login` with no error shown anywhere.
This is the single most likely way a UAT deployment appears broken.

Three ways out, in order of preference:

1. **Terminate TLS in front of the console.** Correct, and what production
   will do anyway.
2. **Reach it over an SSH tunnel.** Browsers treat `http://localhost` as a
   secure context, so `secure` cookies are kept:
   `ssh -L 3000:127.0.0.1:3000 user@uat-host`, then open `http://localhost:3000`.
   Good for one tester, useless for a group.
3. Do not run the console with `NODE_ENV` unset to dodge this. `next start`
   sets it to `production` itself, and fighting that trades a visible problem
   for an invisible one.

```nginx
server {
    listen 443 ssl http2;
    server_name uat.example.com;

    ssl_certificate     /etc/letsencrypt/live/uat.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/uat.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        # The API trusts the proxy for client addresses; this is what it reads.
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 80;
    server_name uat.example.com;
    return 301 https://$host$request_uri;
}
```

The API is deliberately **not** proxied. The console is a BFF: the browser
talks only to it, and it talks to the API over loopback. Exposing the API
publicly is only needed when a mobile or third-party client exists — and then
it needs its own vhost and `CORS_ALLOWED_ORIGINS` set to match.

## 6a. What is listening, and who is believed

Two settings decide the API's exposure, and both default to the safe answer —
so this section is about not undoing them.

**`API_HOST=127.0.0.1`.** After `systemctl start`, check what is actually open:

```bash
ss -tulpn | grep -E ':(3000|4000|5432|6379)'
```

Expect the console on `0.0.0.0:3000` — that is the public surface, behind nginx
— and the API, PostgreSQL and Redis on `127.0.0.1`. If the API shows `0.0.0.0`,
it is reachable from anywhere that can route to the box, and every request then
arrives without passing nginx. It logs a warning at boot when you do that
deliberately.

**`TRUST_PROXY=127.0.0.1`.** This names the proxy whose `X-Forwarded-For` may be
believed, and it is a security control rather than a convenience:

* `false` — nobody is believed. `req.ip` is the socket peer. Correct when
  nothing fronts the API, but behind nginx every request then looks like it came
  from `127.0.0.1`, so the whole office shares one rate-limit bucket.
* `127.0.0.1` — believe the hop that nginx added, discard anything the caller
  wrote themselves. This is what you want for the deployment in §6.
* `true` — believe anybody. **The API refuses to start with this in
  production**, and it is worth knowing why. The per-caller rate limit on
  `/auth/login` keys on `req.ip`; with `true`, `req.ip` is whatever the caller
  put in the header, so a credential-spraying script sends a different address
  on each request and never trips the limit. Measured on this codebase before
  the default changed: 40 of 40 attempts landed against a limit of 30.
* A bare number is refused too. `trustProxy: <number>` was a hop count until
  fastify 5.12.3, which made it trust nobody — a hop count cannot check who the
  immediate peer is. Left accepted, it would look configured and do nothing.

Nginx must be the one setting the header for this to hold. The config in §6
uses `proxy_add_x_forwarded_for`, which appends the real peer to whatever the
client sent — the appended entry is the one `TRUST_PROXY=127.0.0.1` reads.

Verify it end to end after deploying, from another machine:

```bash
# Both should be refused after the limit, NOT let through.
for i in $(seq 1 40); do
  curl -s -o /dev/null -w '%{http_code} ' -X POST https://uat.example.com/api/v1/auth/login     -H 'content-type: application/json' -H "x-forwarded-for: 203.0.113.$i"     -d '{"email":"probe-'$i'@example.invalid","password":"wrong","actor":"ADMIN_USER"}'
done; echo
```

Or run the suite that does exactly this, against a dev box: `npm run
verify:security --workspace @gurukulam/api`.

## 7. Redis, and when to leave it out

Redis backs login lockout only. Without `REDIS_URL` the API falls back to an
in-process store and logs that it has done so — fine for a single-replica UAT,
wrong for more than one, because five failed attempts spread across replicas
never trip a lockout.

Without it, both stores are also **bounded**: they sweep expired entries and
clear themselves at fifty thousand live keys rather than growing without limit.
That bound exists because the keys are chosen by the caller — an address for the
rate limiter, a typed-in email for the lockout — so an unbounded map is a
memory-exhaustion handle on an endpoint that is unauthenticated by design. It
is a backstop, not a plan: a cleared rate-limit store lets a burst through, and
an evicted lockout is a lockout that stopped.

**A configured but unreachable Redis is worse than no Redis.** The lockout
check awaits Redis without a fallback, so if the URL is set and the server is
down, every login attempt returns a 500 rather than failing open. If you are
not confident Redis will stay up on this box, leave `REDIS_URL` unset.

*(Failing open instead would allow unlimited password guessing during an
outage. Which of the two is right is a product decision, not an obvious one —
it is on the open-questions list, not settled.)*

## 8. systemd units

`/etc/systemd/system/gurukulam-api.service`:

```ini
[Unit]
Description=Gurukulam API
After=network.target postgresql.service redis-server.service
Wants=postgresql.service

[Service]
Type=simple
User=gurukulam
WorkingDirectory=/srv/gurukulam/apps/api
EnvironmentFile=/etc/gurukulam/uat.env
ExecStart=/home/gurukulam/.nvm/versions/node/v22.22.2/bin/node dist/main.js
Restart=on-failure
RestartSec=5
StandardOutput=journal
StandardError=journal

NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/srv/gurukulam
# The API writes nothing to disk at runtime — it talks to PostgreSQL and Redis.
PrivateDevices=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
RestrictSUIDSGID=true
RestrictNamespaces=true
LockPersonality=true
MemoryDenyWriteExecute=true
# It only ever needs loopback and the database socket.
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX

[Install]
WantedBy=multi-user.target
```

`/etc/systemd/system/gurukulam-web.service`:

```ini
[Unit]
Description=Gurukulam console
After=network.target gurukulam-api.service
Wants=gurukulam-api.service

[Service]
Type=simple
User=gurukulam
WorkingDirectory=/srv/gurukulam/apps/web
EnvironmentFile=/etc/gurukulam/uat.env
ExecStart=/home/gurukulam/.nvm/versions/node/v22.22.2/bin/npm start
Restart=on-failure
RestartSec=5

NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/srv/gurukulam

[Install]
WantedBy=multi-user.target
```

Absolute paths to the Node binary, because systemd does not read a login shell
and will not find an nvm-managed `node` on `PATH`. Check yours with
`readlink -f "$(command -v node)"`.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now gurukulam-api gurukulam-web
sudo systemctl status gurukulam-api gurukulam-web
```

## 9. Smoke test before handing it over

```bash
# The API answers, and its docs are generated from the contracts it validates
curl -fsS http://127.0.0.1:4000/api/v1/health && echo
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:4000/api/v1/docs

# The console renders its login page
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/login

# The schema is where the migrations say it should be
npm exec --workspace @gurukulam/db -- prisma migrate status
```

Then, in a browser over **https**:

1. Sign in as the bootstrap operator — you should land on the change-password
   screen, not the dashboard.
2. Set a new password; you should land on the dashboard.
3. Settings → Countries → add one. Then a city, a college, a course, a trainer.
   Leave the trainer **Freelance** for now.
4. Batches → create a retail batch. The trainer picker stays disabled until a
   course is chosen, then offers only trainers approved for it.
5. Students → add a retail student → allocate them to that batch. One
   transaction writes the batch mapping, session access, ledger, installments
   and credentials — check the fee ledger shows the advance applied.

That path exercises every invariant that has an enforcement point in the UI.
If step 1 returns you to the login screen with no error, re-read §6.

### The screens added since the first UAT build

Worth walking, because none of them existed when this runbook was first
written and each was a "there is no option to…" on the review:

6. **Batches → your batch → Schedule a session.** Backdating is allowed on
   purpose — it is how a cohort that started two months ago gets its history
   recorded. Mark the session delivered, then attach a YouTube link to it;
   the link field appears only once the session is complete.
7. **Colleges → Requirements → Log requirement.** Confirming one creates the
   college's dedicated batch and links back to it — the batch code appears on
   the requirement row, which is the evidence the flow completed.
8. **Colleges → Contacts** and **Colleges → Portal access.** Both read across
   every college. Contacts shows whether each person can actually sign in;
   Portal access shows every login and why a revoked one was revoked.
   Granting and revoking still happen on the college's own record.
9. **Trainers → edit a trainer → set Engagement to In-house.** Then assign
   them to a batch: they are **confirmed on the spot** rather than proposed,
   the batch gets its primary trainer, and its sessions carry them. The row
   should read "in-house, confirmed without asking" — not as though an answer
   came back. Then **Release** them (a reason is required); the batch is
   unstaffed again and the released assignment stays in its history.
   Approval for the course and the double-booking check still refuse an
   in-house trainer, so try assigning one to two overlapping batches.
10. **Settings → Roles → Add role** and **Settings → Administrators → Add
    administrator.** The new administrator's temporary password is shown
    **once**, on the page. Nothing emails it.
11. **Hiring → Post a job.**

## 9a. The verification suites are not a UAT smoke test

The repository carries fourteen `verify:*` scripts, and they are genuinely
useful — but **every one of them writes to the database it is pointed at**.
They sign in, create records through the API, assert on what came back, and
several delete rows directly to tear their fixtures down. `verify:inhouse`
goes further: it allocates a trainer to a real batch and then releases them.

Run them against a **seeded development database only**. Never against UAT once
testers have put real content in it, and never against production.

```bash
# On a dev box, with the API running and the demo seed loaded:
npm run verify:modules  --workspace @gurukulam/api   # 62 checks
npm run verify:paging   --workspace @gurukulam/api   # 33 — no row lost or repeated
npm run verify:rollups  --workspace @gurukulam/api   # 18 — the cross-college views
npm run verify:inhouse  --workspace @gurukulam/api   # 19 — in-house allocation
npm run verify:contracts --workspace @gurukulam/api  # every response matches its schema

# This one is read-mostly and worth running against a staging box as well: it
# attacks the controls rather than asserting about the code. It does create
# lockout state for invented addresses, which expires on its own.
npm run verify:security --workspace @gurukulam/api   # 15 — see §6a
```

On UAT, §9 is the smoke test. `prisma migrate status` and the three `curl`s are
read-only and safe anywhere.

## 9b. Reading `npm audit` without panicking

`npm audit` on this repo reports ten or so advisories, several of them "high"
and one "critical". That number is honest and almost entirely irrelevant to a
running server, because `npm audit` reports the whole tree — the test runner and
the compiler included — and says nothing about whether anything loads them.

```bash
npm run audit:why     # sorts the advisories by whether they reach the server
npm run audit:prod    # the same tree a production install would create
```

As of this release, measured rather than assumed:

| Advisory | Reaches the running server? | Why |
| --- | --- | --- |
| `vitest`, `@vitest/mocker`, `vite`, `vite-node`, `esbuild` | **No** | Test tooling. The esbuild and vitest issues need their **dev server** running and reachable; production runs `node dist/main.js` and `next start`. |
| `prisma`, `@prisma/config`, `deepmerge-ts` | **No** | The Prisma **CLI**, used by `migrate` and `generate`. `@prisma/client` — the part the API loads — has no dependencies at all. The advisory is a stack overflow from a recursive config file, which means it needs someone who already edits your config. |
| `postcss` (under `next`) | **Build only** | Verified by tracing every module the production server loads while serving pages: `next/node_modules/postcss` is loaded **zero** times. It processes your own CSS at build time. The advisories need attacker-controlled CSS input. |
| `next` | **Yes, it is the server** | Kept current within 15.x. Clearing the postcss advisory outright means Next 16, which is a compatibility exercise rather than a security one. |

**None of them is a remote-code-execution path**, which is what an attacker
would need to run a miner, install a backdoor, or read your database. The worst
of them is an arbitrary *file read* against a development server that a
deployment does not run.

To make a production box match that reasoning physically rather than only
logically, prune after building:

```bash
npm run build
npm prune --omit=dev          # removes vitest, vite, esbuild, the Prisma CLI, tsc
sudo systemctl restart gurukulam-api gurukulam-web
```

The trade-off, and it is a real one: this also removes the **Prisma CLI** and
`tsx`, so `npm run db:deploy` and `npm run bootstrap` stop working until the
next `npm ci`. Run migrations and create the first operator **before** pruning,
and accept that a redeploy reinstalls everything anyway (§10). On a box where
the same checkout is used to build and to run, pruning buys you less than it
costs; on one where the build happens elsewhere, prune.

### What would actually get a server mining

None of the above. In practice a Linux box gets a miner through one of these,
and all of them are configuration rather than dependencies:

```bash
# 1. A service listening where it should not be. Redis with no password on a
#    public interface is the single most common way an EC2 box starts mining —
#    it allows writing arbitrary files, which becomes a cron entry.
ss -tulpn | grep -v '127.0.0.1\|::1'

# 2. What the security group actually allows in. Only 80 and 443 should be open
#    to 0.0.0.0/0; SSH should be your address, and 4000/5432/6379 nothing.
#    (Check in the AWS console — the box cannot see its own security group.)

# 3. Redis reachable without a password.
redis-cli -h 127.0.0.1 ping && redis-cli config get requirepass

# 4. Password SSH and root SSH — both should be no.
sudo sshd -T | grep -E 'permitrootlogin|passwordauthentication'
```

And to check whether something is already running:

```bash
ps aux --sort=-%cpu | head -15          # a miner does not hide its CPU use
ss -tunp | grep -vE '127.0.0.1|::1'     # outbound to a pool, on an odd port
crontab -l; sudo crontab -l; ls -la /etc/cron.*/   # how they survive a reboot
sudo journalctl -u ssh --since '7 days ago' | grep -c 'Failed password'
```

A miner is loud: sustained high CPU from a process you do not recognise, often
out of `/tmp`, `/dev/shm` or `/var/tmp`, with an outbound connection it keeps
re-establishing. If `ps` and `ss` are clean and nothing unexpected is listening,
the audit output is not telling you that you have one.

## 10. Redeploying

```bash
cd /srv/gurukulam
git pull
npm ci
set -a && . /etc/gurukulam/uat.env && set +a
npm run db:deploy
npm run build
sudo systemctl restart gurukulam-api gurukulam-web
```

Migrate before building, and build before restarting: the running code should
never be newer than the schema underneath it.

This release's migrations only add columns with defaults (§4), so the order
above is enough — the previous build keeps running correctly against the new
schema for the few seconds between `db:deploy` and the restart.

There is no zero-downtime story here and UAT does not need one — the restart is
a couple of seconds. Production will want two API replicas behind the proxy and
a rolling restart, which is also the point at which Redis stops being optional.

## Building behind a firewall

`next build` fetches **Plus Jakarta Sans** and **JetBrains Mono** from Google
Fonts, because `app/layout.tsx` uses `next/font/google`. A box with no egress to
`fonts.googleapis.com` and `fonts.gstatic.com` fails the build with:

```
`next/font` error: Failed to fetch `Plus Jakarta Sans` from Google Fonts.
```

Three ways through, in order of preference:

1. **Build somewhere with access** and ship `apps/web/.next` to the host. The
   build is the only step that needs the internet; running needs none.
2. **Allow those two hosts** through the proxy for the build.
3. Behind an HTTP proxy, make sure `HTTPS_PROXY` and `NODE_EXTRA_CA_CERTS` are
   exported. `turbo.json` passes both through to tasks — without that
   declaration Turbo's strict env mode strips them, and `npm run build` fails
   while `npx next build` in `apps/web` succeeds, which is a maddening thing to
   debug.

Self-hosting the two fonts with `next/font/local` would remove the dependency
altogether. Worth doing before production; it is a change to the design system's
font loading, not to deployment.

## What this deliberately does not cover

Email, WhatsApp and S3 are not integrated, by design. Certificate PDFs are not
generated. Payments are recorded, never collected — there is no gateway.

**Every credential this console issues is shown once, on the page, and nothing
emails it.** That is true of a college portal login, a new administrator, and a
password reset. The API returns the temporary password a single time and stores
only its hash, so nobody can retrieve it afterwards — losing it means issuing a
new one, which invalidates the old. Whoever runs UAT needs a way to pass these
on.

The college, trainer and student portals themselves are deferred. The API
accepts a `COLLEGE_USER` login today and the scope works, but there is no portal
UI behind it, so UAT covers the admin console only.
